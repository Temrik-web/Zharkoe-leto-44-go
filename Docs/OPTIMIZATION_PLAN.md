# План оптимизации Жаркое лето 44-го

Дата: 5 сентября 2026. Это план измерений и изменений, а не отчёт о достигнутом ускорении. Реальных замеров CPU/GPU, FPS и памяти пока нет.

## 1. Зафиксировать воспроизводимый сценарий

Выбрать минимальный целевой ПК и записать CPU, GPU, RAM, разрешение, профиль качества и версию драйвера. Предварительная цель для обсуждения — 1920×1080, 60 FPS: бюджет кадра 16.7 мс. Для слабого профиля можно отдельно принять 30 FPS / 33.3 мс; не смешивать результаты разных профилей и компьютеров.

Собрать Windows Development Build для профилирования, без Deep Profile. Для сравнения кадров временно убрать VSync/ограничитель FPS; для итогового игрового прогона вернуть выбранные настройки. Проверить также обычный release-билд, поскольку редактор и диагностическая сборка имеют другую стоимость.

Маршрут на 3–5 минут: старт → прогулка между домами → интерьер с фонариком → бой с четырьмя врагами → несколько взрывов → подбор/выбрасывание предметов → открытие и сортировка инвентаря. После прогрева повторять маршрут минимум три раза. Нагрузку с 10 и 20 врагами проверять в отдельной тестовой сцене, не меняя основной уровень.

Собирать: median/p95/p99 времени кадра, CPU Main/Render Thread, GPU frame time, GC Alloc, паузы GC, batches/SetPass, число видимых треугольников, память текстур/мешей/аудио, рост памяти после повторения маршрута. Отдельно отмечать время загрузки и первый выстрел/взрыв.

Результат этапа: таблица baseline и три наиболее дорогих участка с захватами Unity Profiler, Frame Debugger и Memory Profiler. Средний FPS без распределения времени кадра недостаточен.

## 2. Рендеринг, освещение и окружение — первый кандидат на GPU-проверку

В `QualitySettings` выбран третий профиль. Его `High Fidelity_PipelineAsset` использует MSAA 4×, render scale 1, карту теней основного света 4096, до восьми дополнительных источников на объект, soft shadows и shadow distance 40. Это кандидаты для сравнения, не доказанные причины просадок.

Проверять по одному изменению:

- MSAA 4× → 2×; сравнить GPU time и мерцание мелких деталей.
- Тени основного света 4096 → 2048; сравнить качество в интерьере и на улице.
- Ограничить дополнительные источники и теневые источники там, где это даёт видимую экономию. Фонарик проверять отдельно.
- Для неподвижного окружения сравнить baked/mixed lighting, Light Probes для персонажей и Reflection Probes для помещений. Не запекать без решения, нужна ли динамическая смена суток.
- LOD для домов, деревьев и крупного декора; дальности травы и мелких объектов; occlusion culling для плотной застройки. Проверить исчезновение объектов при переходах и стоимость памяти.
- Проверить SRP Batcher, совместимость материалов и GPU instancing повторяющихся моделей. Не объединять весь уровень в один меш: это ухудшает отсечение невидимого.

Критерий: снижение GPU/Render Thread time на том же маршруте без заметной потери читаемости и артефактов. Сохранить осмысленные Low/Medium/High профили; удалить настройки только после проверки ссылок.

## 3. Бой, физика и эффекты — убрать пики во время стрельбы

`HitscanWeapon.TryFire` использует `Physics.RaycastAll` и сортировку. Граната создаёт массивы пересечений, словарь целей и лучи проверки укрытия. Эффекты попаданий создаются через Instantiate/Destroy. Это конкретные места для CPU/GC-профилирования.

- Если RaycastAll заметен в профиле — переходить на переиспользуемые буферы. При заполненном буфере нужен безопасный fallback или расширение: молчаливое усечение может пропустить ближайшую стену и изменить бой.
- Пулы эффектов попаданий, дыма, вспышек, дырок от пуль, гильз и гранат; задать предел активных объектов и время жизни. Для каждого пула определить сброс Rigidbody, коллайдеров, запала, подписок и состояния урона.
- Уменьшить слои, участвующие в поиске целей и укрытий. Проверять попадания, двери, укрытия и коллайдеры костей после каждого изменения масок.
- Ограничить длительность/количество прозрачных частиц и теневых источников во взрывах. Измерять overdraw, особенно в помещении и при нескольких гранатах.
- Отключить подробные боевые Debug.Log в обычном билде; сохранить полезные предупреждения о некорректной конфигурации.

Критерий: снижение p95/p99 в бою, отсутствие роста памяти после повторных взрывов, прохождение регрессионных тестов. Цель 0 B/frame относится к установившемуся горячему циклу, а не ко всем меню и загрузке ресурсов.

## 4. ИИ и навигация — масштабирование числа врагов

Восприятие уже выполняется с интервалом около 0.15 с и небольшим случайным сдвигом, поиск целей использует NonAlloc. Не переделывать это без замеров.

- Сравнить 4/10/20 врагов: отдельно восприятие, поиск маршрутов, анимацию и физику.
- Для удалённых врагов снижать частоту восприятия/перестроения маршрута; не отключать реакцию на близкий выстрел, урон и сюжетные события.
- Проверить запечённый NavMesh. Fallback-навигация в `EnemyMotor` делает дополнительные проверки земли и препятствий; измерять её отдельно, не использовать вместо корректного NavMesh на готовом уровне.
- Вводить реестр персонажей только если поиск становится заметной нагрузкой. Следить за регистрацией/удалением при спавне, смерти и перезагрузке.
- При необходимости распределить дорогие запросы по кадрам с ограничением задержки реакции.

Критерий: выбранное количество противников помещается в бюджет CPU; противники не теряют игрока из-за редких проверок и не застревают в дверях.

## 5. UI, ресурсы и размер сборки

Ячейки инвентаря уже переиспользуются (`EnsureSlotViews`), поэтому повторно внедрять для них пул не требуется. Измерить Canvas rebuild, раскладку, сортировку, обновление текста и открытие панели. Обновлять только изменённые данные, если полный Redraw действительно дорог.

По Memory Profiler найти самые дорогие текстуры и меши. Для каждого проверить максимальный размер, компрессию под Windows, mipmaps, Read/Write, MeshCollider и необходимость несжатого аудио. Музыку и длинные записи сравнить со streaming. Не снижать все текстуры одним массовым правилом.

В manifest одновременно есть URP и HDRP. Рабочий рендеринг — URP, но HDRP удалять только после проверки материалов, VFX Graph и зависимостей. Само наличие пакета не доказывает нагрузку на кадр; смотреть Build Report и шейдерные варианты. Демо-сцены и примеры ассетов оценивать по фактическому попаданию в билд.

Критерий: меньше памяти/размер билда/время загрузки без розовых материалов, пропавших эффектов и сломанного UI.

## Порядок итераций

1. Рабочий билд + baseline + целевой ПК.
2. Самый дорогой участок по измерениям: GPU либо бой/CPU, а не оба сразу.
3. Повторный профиль и регрессия боёвки; принять или откатить изменение.
4. Масштабирование ИИ, затем память и размер сборки.
5. Проверка release-билда и фиксация контрольного маршрута для будущих сравнений.

На каждую оптимизацию — отдельный коммит и запись: причина, настройка/код, одинаковые условия сравнения, показатели до/после, визуальные/игровые компромиссы. Рефакторинг крупных классов вести отдельно от измеряемых оптимизаций, чтобы не приписывать ускорение изменению структуры кода.
